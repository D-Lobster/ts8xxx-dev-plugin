# TS800X 已有项目维护

## L1 快速通道

明确的日常修改按 WORKFLOW.md L1，仅做定向阅读/风险检查、build 0/0 与按需烧录验证；不强制全量 Code Map、依赖分析、终审。下列完整步骤用于 L2/L3 或需要深入排查的任务。

## 开始前

1. 检查 `git status`；所有未提交修改都视为用户资产，不覆盖、不清理。
2. 读取项目说明、`PROGRESS.md`、`MEMORY.md`、构建配置和目标模块。
3. 使用 `ts800x-code-reader` 生成或更新 `context/code_map.yaml`。
4. 运行基线 build 0/0，并记录现有日志/行为；基线失败先报告，不能把旧问题算作本次修复。
5. 运行变更前依赖分析，识别 ISR、公共全局、协议、Flash、低功耗和 `.uvprojx` 风险。

## 方案 Gate

对接口、硬件映射、状态机、多个文件或行为有影响时，先提交方案：

- 当前执行链和根因；
- 拟改文件/符号；
- 保持不变的行为；
- 风险、回滚和测试；
- 是否参考旧项目，以及 R25 逐行 diff 方法。

用户确认后才实现。编译修复或明确的单行配置可快速通道，但最终验证不减少。

## 逐任务修改

把改动拆成可单独验证的小任务，每个任务执行：

```
最小 diff → integrate → build 0/0 → 按需 flash/log 快速测试
→ code-quality → build 0/0 → dependency report
→ flash/log/regression → verified/pending
```

- 只改当前任务需要的代码，不顺手重构无关区域。
- SDK 只读；移植逐行对照源项目，记录差异及理由。
- 回归日志与基线对比，区分预期变化和意外变化。
- 硬件不可用时只标记 `[待硬件验证]`。

## 收口

1. 最终 build 0/0。
2. `git diff` 与变更后依赖分析。
3. 检查原有功能、错误路径、低功耗和协议兼容性。
4. L3 执行 ts800x-build Rebuild、全量 APP 扫描、依赖分析和 ts800x-final-reviewer；日常维护按 L1。
5. 更新项目状态，列出基线旧问题、已修问题和剩余风险。

未明确要求时不提交、不推送；不得用破坏性 Git 命令恢复用户工作区。
